# Taste — Command Code agent
- Expects work to be verified by actually running the required build and test commands before completion is claimed; "done" means those commands pass, not that they probably would. Confidence: 0.92
- Explicitly prohibits fabricated results: if a toolchain step fails, iterate until it passes or report the exact blocker and stop, rather than pretending. Confidence: 0.95
- Requires a final report that lists files created/changed, exact test output (pass/fail counts), build result, and every deviation from the spec with its reason; for bug work also the real root cause, the red→green evidence, and a short list of remaining manual checks. Confidence: 0.9
- Wants all work confined to the given project root: no global install scripts, no modifying anything outside the workspace, no touching system/keychain state beyond the app's own in-code keychain usage. Confidence: 0.85
- Prefers no git history from the agent — at most a single local initial commit, otherwise leave the repo untouched. Confidence: 0.75
- Git workflow convention: new features are developed on `feature/<short-name>` branches and committed there; `main` only receives completed features (it should always build and pass tests). Work already finished goes straight to `main`, and the feature branch name is reported back on handoff. Confidence: 0.85
- Never pushes to the remote — the user handles `git push` themselves; committing locally and then stopping (reporting commit hash + `git log --oneline`) is the expected end state. Confidence: 0.8
- `.gitignore` should exclude only build products and local state (build/, DerivedData/, xcuserdata, *.xcuserstate, .DS_Store) — never source, project files, tests, plans/briefs, scripts, or docs. Confidence: 0.75
- Team-wide/process conventions should be written into the repo's docs (e.g. a top-level "Development" heading in README.md in the same pass they're agreed), not just followed silently. Confidence: 0.7
- Provides a plan/brief document as the "spec of record"; expects it to be read first and followed, with decisions it marks as locked treated as non-negotiable and not revisited. Feature briefs arrive as a structured template — verbatim user quote, an "Interpretation (build exactly this)" numbered list, then "Tests / evidence" and "Constraints" (sometimes a branch directive) — and every section is binding: build exactly the stated interpretation, satisfy the named test cases verbatim, and do not substitute your own reading. Confidence: 0.85
- Bug reports arrive as a pre-investigated brief: verbatim user quote, "What I already ruled out" (static traces with file:line references), a ranked list of hypotheses to discriminate between, a required approach ("reproduce FIRST, then fix"), constraints, the exact verification commands, and a handoff. The ruled-out list is binding prior work: don't re-derive it and never re-assert static wiring as proof it works — spend the effort on runtime discrimination instead. When the report is ambiguous about the cause (e.g. wrong action firing vs. the glyph just looking wrong), say which one is actually true with evidence before fixing. Confidence: 0.8
- Presentation changes must not regress existing behavior: raw copied text stays the searchable/preview field even when the card renders something richer, and existing action availability (e.g. which actions are hidden for a kind) is preserved. Confidence: 0.65
- New UI features must hold in both full-size and compact layouts — compact shrinks dimensions and type size but never drops content or information. Confidence: 0.6
- Wants explicit deviation reporting instead of silent scope changes when the spec is impractical. Confidence: 0.8
- Prefers depending on a protocol boundary (e.g. a backend protocol with capabilities + a registry) so concrete clients are swappable and the UI never talks to a vendor client directly; new provider features should be expressed as capability flags + protocol methods rather than UI special-cases. Confidence: 0.8
- Expects documentation to stay in lockstep with the code: README, TESTING.md and the originating plan/brief docs must be updated in the same pass whenever a backend, endpoint, error state or limitation changes. For a new feature that means a README feature bullet plus project-map entries, a suite-by-suite test-count list and a dedicated manual-checklist section in TESTING.md, and a `Docs/verify-<topic>.png` reference capture. Confidence: 0.8
- When a third-party integration is replaced, wants it removed wholesale — old client, service URLs and naming deleted rather than kept as shims; the former vendor may survive only as documented UX inspiration. Confidence: 0.65
- Favors local-first implementations (local SQLite/file storage) with no cloud sync unless asked. Confidence: 0.6
- Wants new features split along the existing models/services/UI layering, with the decision logic in plain, dependency-injected service types (parsers, caches taking an injected clock/directory) and thin views, so the logic is unit-testable without the UI. View styling constants and tint/color math belong in pure, UI-free types so the rendered values (composited colors, opacities) can be pinned by unit tests without a UI harness. The same applies to layout and interaction geometry: drag/resize height math and card/thumbnail sizing (card width → inner content width, height from an image's aspect ratio) are extracted into pure static functions pinned by unit tests with concrete expected numbers (wide/standard/tall/square/degenerate zero cases) rather than living only inside a SwiftUI view or gesture closure. Confidence: 0.85
- Insists UI-critical paths never block on I/O: network fetches and image/icon processing run off the main thread behind caches (memory + disk), with in-flight request dedupe and placeholders instead of spinners that stall scrolling. Confidence: 0.75
- Likes bounded, self-protecting resources rather than unbounded growth: explicit timeouts and byte caps, TTLs, negative caching of failures, and an LRU size cap, plus a user-facing setting/button to toggle or clear the cache. Confidence: 0.7
- Expects new behavior to respect existing app-wide modes (e.g. a privacy "pause" that must also suspend network fetches) rather than only the happy path. Confidence: 0.7
- Bug diagnosis must start with reproduction against real data, not speculation: write a throwaway diagnostic (scratch script or test) that exercises the real inputs/paths and prints the actual values before any code is touched. A matrix over every suspect input × pasteboard-flavor/path combination is the preferred shape (so the competing hypotheses are discriminated cell by cell), and the same matrix is re-run after the fix as before/after evidence; the failing tests are added and their red output quoted before any fix, then re-run green. Confidence: 0.85
- When fixing a bug, wants only the root cause fixed — explicitly "no speculative rewrites" and no UI redesign — with the true root cause named in the final report (including the case where the code was correct and the observed behavior had an environmental/input explanation). Confidence: 0.85
- Regression tests must be designed so the observed failure can never pass again: cover the other axes (e.g. blue/green alongside red, or all alternative branches), not just the single case that already worked. Confidence: 0.8
- Expects visual/manual evidence artifacts committed into the repo (e.g. a `Docs/` screenshot or rendered overlay image) for anything UI-facing, and an explicit statement when capturing evidence is impossible in the environment — never a claimed visual confirmation that wasn't actually done. Confidence: 0.8
- Bug fixes go straight to `main` once the build+test gate passes (no feature branch), unlike new features, and the commit message states the actual root cause rather than a generic "fix bug". When the brief names a branch (e.g. a bug fix belonging on the feature branch that introduced the code), that directive wins: commit on the current branch — and honour the named base commit too, e.g. a fix that depends on harness/test work already landed on the current feature branch is branched from that HEAD, never from `main`. Confidence: 0.8
- Reports bugs terse: often just the raw error text (e.g. a pasted Xcode "Cannot find 'X' in scope" line) or one plain sentence of symptom (e.g. "the app window flickers when I drag it up to increase its height", "it is still deleting the clipboard item directly") with no repro steps, environment, or expected behavior — expects the agent to reproduce from that alone and state whether the code or the local/IDE state is at fault. Confidence: 0.65
- High-frequency interaction paths (drag, resize, scroll) must not perform persistence or global state churn per event: no UserDefaults writes, no whole-app state republish, no re-applying app-wide settings like activation policy inside the event handler. Live drag only mutates the visual surface; the value is committed once at gesture end, and idempotent app-wide settings changes are guarded with a no-op check when already correct. Confidence: 0.7
- Caches keyed by a computed id must be versioned/invalidatable (version suffix or marker file with a one-time clear) so stale data written by older builds can never be silently reused. Confidence: 0.7
- Verification claims must not exceed what the evidence actually shows: the user independently re-checks committed screenshots (vision pass / pixel sampling) and will re-open the task when a "visually confirmed" claim isn't visible in the image. Say plainly if the visual result still doesn't show. Confidence: 0.9
- When a previous conclusion is disputed, reproduce and instrument the LIVE path instead of re-asserting the diagnosis — temporary env-gated logging of the actual values (e.g. per-bundle-id accent reaching the view, whether the revision bump really re-renders) is welcomed, but all instrumentation must be stripped before commit. Confidence: 0.8
- Wants UI styling changes to be clearly perceptible, not technically-present-but-invisible: treat a color/accent request as a visibility spec with concrete numbers (~0.5–0.8 opacity border, ~0.10–0.15 background wash) while keeping state distinctions (selected vs unselected) obviously different. Confidence: 0.75
- Async render paths must be deterministic enough to certify: after warm-up/cache load, data should be present before or shortly after first paint, with no cards stuck on nil values — and the refresh chain (revision → observable object → view) must be proven, not assumed. Confidence: 0.7
- Media previews must show the whole image: sizing comes from the source format's own dimensions (e.g. Open Graph 120:63 / 1200×630) or the image's true aspect ratio, never a hardcoded fixed height combined with `.fill` + `.clipped()` — a fixed height that crops or distorts gets reported as a bug ("the aspect ratio of the image is very weird. Use full width of the card, height should be auto"). Thumbnails span the card's full inner width with height derived from the image's aspect ratio, implemented once in a shared helper used by every kind that renders an image (e.g. `.image` snapshots and `.file` image thumbnails), and correct in normal + compact and light + dark. Confidence: 0.8
- "Auto" applies per axis, not to the whole box: the unconstrained dimension is derived from the data and the other dimension is bounded. A fully unbounded result is a placeholder expectation, not the end state — an uncapped tall thumbnail (600×1800 → ~1008 pt card overflowing the panel) gets rejected on the next round ("when it is tall (portrait), width should be auto too"), so size to contain inside (full inner width × sensible max height) rather than letting one axis run free. On the first pass do not silently clamp: state the resulting magnitude, ship data-driven sizing, and flag any cap as a deviation for the user to confirm or remove. Confidence: 0.8
- Standard text-editing keys must never be shadowed by app-level shortcuts: while a text field has focus, Backspace/Space/arrows must edit the text (caret movement), and destructive or item-level actions move to ⌘-modified equivalents (⌘⌫ delete, ⌘Y preview) instead of bare keys. Confidence: 0.8
- Global key-monitor fixes must cover the whole class of intercepted keys, not just the one reported — a Backspace fix is expected to also handle Space and ←/→ (and the user will notice when it doesn't). Confidence: 0.8
- Prefers routing input from the UI framework's authoritative focus state (SwiftUI `@FocusState` mirrored into app state) over heuristics such as inspecting AppKit first-responder classes, which proved unreliable for SwiftUI field editors. Confidence: 0.7
- Swift 6 concurrency diagnostics must be fixed properly, never suppressed: explicit capture lists (`[self]` / `[weak self]`), immutable locals instead of captured `var` in `Task.detached`/`Task {}` closures, and adjusted isolation. Explicitly bans `@unchecked Sendable`, `nonisolated(unsafe)`, or reverting the Swift language mode as escape hatches — and expects the whole target grepped for the same pattern so the codebase is Swift-6-clean even while `SWIFT_VERSION` stays 5.x. Confidence: 0.85
- Compiler warning counts are treated as a tracked metric: report the `xcodebuild` `warning:` count before vs after a fix, and account for any remaining warning (e.g. toolchain-only notices) rather than claiming a bare "0 warnings". Confidence: 0.75
- Performance claims must be quantified, not asserted: instrument every hop of the pipeline (event observed → DB committed → UI published), actually run it, and quote real numbers — p50 plus individual samples against the stated target — in the final report, then strip the temporary instrumentation. Confidence: 0.8
- Perceived responsiveness is a first-class requirement: a newly copied item must appear essentially instantly (stated target <150 ms p50), reached by shortening the poll interval, publishing the already-known pipeline result instead of re-querying, and preventing OS background throttling (App Nap) from delaying updates — not by adding loading affordances. Confidence: 0.7
- Enriching an item should cost a single fetch: one page request must yield all metadata (image + title + description), with the complete record persisted in the existing cache, rather than a second request just for metadata. Confidence: 0.65
- Wants platform-event hacks scoped to the exact views that need them: no global `NSEvent` swizzling, no whole-app event hooks. Prefer a per-view mechanism (an `NSViewRepresentable` that registers only its own scroll views, gated by hit-testing the pointer) so no other part of the app is affected. Confidence: 0.65
- Native OS/AppKit behaviour must be preserved rather than reimplemented: natural-scrolling direction, precise deltas vs line-based deltas, trackpad momentum glide (`phase`/`momentumPhase`), and existing system mappings like Shift+scroll all keep working, with the already-native case left to AppKit instead of being intercepted. Confidence: 0.65
- When a behaviour can't be physically verified by the agent (mouse/trackpad input), wants an automated synthetic-input test (e.g. constructing a synthetic `NSEvent` and asserting the effect) if at all feasible, and otherwise a plain statement that manual verification is still required plus short numbered manual test steps (device/gesture → expected result). Confidence: 0.7
- Scopes requests into must-have vs optional surfaces: the named primary target is binding, while a secondary/related surface is touched only if it's low-risk — measured changes stay focused on the primary instead of a broad sweep. Sibling elements explicitly declared out of scope (e.g. "paste, pin and ellipsis stay as-is") must survive untouched — no opportunistic restyling of the neighbours even when a shared helper would be tidier, and no new files unless one is genuinely cleaner (and then it must be registered in the pbxproj). Confidence: 0.75
- New input handling must not regress the existing pointer interactions it overlays: card click/selection and context menus keep working, and the added handling only claims events that would otherwise do nothing. Confidence: 0.6
- Warning/diagnostic-only cleanup requests are expected to be provable no-op refactors scoped to exactly the flagged site: no logic or control-flow changes, no drive-by cleanups elsewhere in the file, dependency installs/package updates are out of scope, and the change is described as warning-only. If the reported diagnostic does not reproduce, still make the requested harmless change but state plainly that it didn't reproduce (with the compiler settings observed) and name the likely local cause — stale editor diagnostics, DerivedData, or a different build configuration — rather than pretending the warning reproduced.
- Third-party design references (e.g. a lucide icon) are to be reproduced natively from the library's own path/grid data as a SwiftUI `Shape` — never by adding a JS/SVG-file/font/asset dependency to a native app. Stroke geometry follows the source spec (stroke width 2 of a 24-unit grid, round caps/joins), the glyph inherits `foreground`/currentColor so it matches its neighbours' weight, and it scales from the size already passed in so compact and full-size layouts both look right. Confidence: 0.75
- Passing-test count is a tracked invariant: after a change the full suite's test count must not drop (ideally identical), plus the filtered `grep -E "(warning|error)"` for the touched file must print nothing. Confidence: 0.75
- Non-reproducing test failures are reported, not buried: when the full suite shows a failure in an unrelated test, re-run it in isolation, re-run the whole suite, and if it passes state plainly in the handoff that it was a flake (naming the test) — the same honesty applies to toolchain flakes, which should be diagnosed (stale DerivedData / code-signing on the xctest subcomponent → `clean` and retest) rather than claimed as a pass. A green suite is never reported while a known failure is unexplained. Confidence: 0.75
- For purely visual changes, expects the agent to self-check the actual rendering (offscreen/high-scale `ImageRenderer` preview compared against the neighbouring chrome at both normal and compact sizes and in both light and dark appearance) saving the rendered PNG under `/tmp` (cropped/zoomed further when the details are small, and covering every variant incl. pin in both states) so the operator can open it himself, and then explicitly hand the final aesthetic judgment to the user rather than declaring it visually approved. For geometry changes the renders must also sweep the extremes of the input space — e.g. wide, standard, tall and square aspect ratios for every affected card kind (plus a close-up of the clamped/capped variant so its markers stay legible) — with in-image markers/dimension labels proving nothing is cropped, and the report must state what each PNG shows (per-variant widths and heights, and the cap/boundary rule chosen). When a follow-up changes one variant, re-render the PNGs with the changed case next to an unchanged control (e.g. the full-width landscape pair alongside the newly centered portrait pair) so the no-regression claim is visible in the same image. Confidence: 0.85
- Peer elements in a chrome row must look identical: no accent/primary emphasis on a single button (accent fill + accent border) while its siblings are plain — background wash and hover treatment come from one shared neutral style (`Color.primary.opacity`), and "primary/CTA" styling is not a per-button flag to sprinkle on individual actions. Confidence: 0.7
- Dead code is to be deleted once it is genuinely unused: when the last caller stops passing a parameter, remove the parameter and its now-unreachable styling branches (e.g. a border overlay that is always clear) rather than leaving them in place — but only after grepping every call site; if other callers still pass it, keep the parameter and just stop passing the value. Confidence: 0.7
- Verification gates are re-issued verbatim across rounds (same `grep -E "(warning|error)" | grep -i <file>` printing nothing, same `tail -5` showing `** TEST SUCCEEDED **` and the unchanged test count, same 8× offscreen footer render to a `/tmp` PNG covering normal + compact) and the handoff must report files changed, the agent's own quoted build/test output, and the PNG path. Confidence: 0.65
- Follow-up UI requests are incremental refinements of the previous commit, not rewrites: extend the abstraction already in place (e.g. adding cases to the existing glyph enum and reusing its stroke style) rather than introducing a parallel structure, and leave prior work that already matches the stated spec untouched. Confidence: 0.65
- Any element whose size cap leaves it narrower than its container must be horizontally centered (mx-auto / `maxWidth: .infinity, alignment: .center`), not leading- or trailing-aligned; the full-width case stays exactly as-is. An alignment the agent picks on its own — even when flagged as a deviation for approval — is likely to come back as a correction ("centered, NOT leading-aligned"), so default an under-filled box to centered. Confidence: 0.75
- Presentation follow-ups are surgical: an alignment/positioning change must leave the pure sizing/geometry math untouched ("keep the pure thumbnailSize math untouched") and touch only the tests that actually pin the changed behaviour, updating docs to the new wording. Confidence: 0.7
- For new features, demands an interactive design phase BEFORE any code: explore the codebase first, then ask clarifying questions one at a time (multiple choice preferred) and wait for each answer instead of batching or self-deciding, then present 2–3 approaches with trade-offs and an explicit recommendation, get approval section by section, and only then branch and implement. The gate is hard: no code, scaffolding, or implementation while design questions remain unapproved. Confidence: 0.85
- Design and plan artifacts follow the repo's own established doc layout rather than a new format: an approved design goes to `Docs/superpowers/specs/YYYY-MM-DD-<slug>-design.md` and is committed (on `main`) before the feature branch is created, then a task-by-task checkbox plan to `Docs/superpowers/plans/YYYY-MM-DD-<slug>.md`; new docs should mirror the section structure of the existing ones. Confidence: 0.8
- Dependency minimalism is a standing constraint: the app deliberately has a single third-party package (GRDB), and adding another (even a well-known highlighter/parser) is heavily disfavored — native platform APIs (`AttributedString`/`Text`/AppKit) are the default, and a package only after the native alternative is shown to be materially worse. Confidence: 0.75
- The clipboard capture hot path is sacred: nothing derived or expensive (detection, tokenizing, parsing, highlighting) may run on the monitor/capture loop — such work is lazy at first render, off-main, bounded by explicit char/line caps, and cached per item so repeated renders cost only a lookup. Confidence: 0.8
- Prefers automatic heuristics paired with a per-item override in the UI (context-menu "force on / force back to default", persisted) over a global settings toggle, so a wrong guess can be corrected item-by-item; genuinely ambiguous heuristics should err toward not acting (conservative thresholds, negative cases pinned by tests). Confidence: 0.6
- Type-detection/classification must be conservative and never turn prose into a rich card: only an unambiguous whole-string value may classify as a special type (a sentence containing `#ff0000` stays text), and every newly supported notation ships with its own false-positive guard pinned by negative tests — e.g. bare hex requires both a hex letter and a digit so `20240101`, `123456`, `deadbeef` and `facade` stay text. Confidence: 0.7
- Carefully separates a regression (behavior that used to work) from a genuine feature gap (a format/notation that was never supported) and expects that distinction stated explicitly — a never-supported case must not be described as "broken" — while both get closed out in the same change. Confidence: 0.8
- When the brief explicitly delegates a decision ("decide and state", "pick one, document it, test it", "make the call based on your repro"), settles it himself instead of asking: choose one documented convention (e.g. CMYK components on a 0–100 scale, `%` equivalent), ground the choice by tracing the real call path rather than by preference, state in the report the concrete consequence of each option (e.g. exactly what each alternative would paste), write the convention into code comments, tests and user docs, and list the deliberately unsupported variants in the handoff. Confidence: 0.8
- Adding a notation/format means threading it through the existing pipeline rather than special-casing: extend the shared token-splitter/alpha handling and the existing regex/switch so old notations keep identical behavior, rather than bolting a parallel parser next to them. Confidence: 0.7
- Paste semantics are a hard constraint that outranks the preferred classification/rendering approach: before changing which kind an item gets, trace what each kind actually writes to the pasteboard (file URL vs raw PNG vs text vs RTF) and state in the report what each option would paste, then pin it with tests asserting the real `NSPasteboard` types. An adjacent violation of that same constraint discovered while tracing (e.g. a text override that bypassed every kind-specific paste branch) is fixed in the same change rather than just noted. Confidence: 0.8
- Repro and regression tests extend the existing harness/suite for the affected subsystem (e.g. new cases in the already-existing synthetic-snapshot reader tests) instead of standing up a parallel new test file; temporary matrix printers and evidence renderers are stripped before commit, and the kept tests remain the documentation of the decision. Confidence: 0.7
- Filesystem-path strings are classified by a bounded whole-string guard (whole string only, single line, ~4 KB cap, absolute path or `file://` URL) plus a cheap existence + UTI/extension check on the background capture queue — never loading image data at capture — with the negative cases pinned by tests as unchanged: missing file, directory named `*.png`, non-image extension, multi-URL list, and prose containing a path. Confidence: 0.75
- When a brief asks to "check and report honestly" on a suspected cause, verify it and report the verified truth even when it contradicts the suspicion (e.g. retention deletes only DB rows and therefore leaks payload files; an orphan-pruning routine exists but is never called), listing such adjacent findings in the handoff rather than silently fixing or papering over them. Confidence: 0.75
- A feature only counts as shipped when the whole chain exists: store method → AppState wrapper → visible UI affordance. A working store method with zero callers (no AppState method, no menu item, no sheet) is reported and fixed as the bug itself, and any field the UI lets the user write must be rendered somewhere — persisted-but-never-displayed data (an item `title` written by "Rename…" but ignored by the card preview) is treated as a real defect, not a cosmetic gap. When that is the finding, say plainly that the reported path (add/filter) already worked and label the actual gaps. Confidence: 0.8
- Any successful mutation must leave published/derived state consistent with the database immediately — after add, remove, rename, create and delete — with cleanup of dependent state (clearing a filter id when its board is deleted), verified by asserting right after the call instead of waiting for an unrelated event; and a search/filter legitimately hiding an item must be demonstrated as recoverable (clearing the query shows it again) and pinned by a test. Confidence: 0.75
- Modal edit sheets follow the existing sheet conventions rather than inventing new ones: prefilled with the current value, input trimmed, primary button disabled while empty, cancel/default keyboard shortcuts, dismiss on success, and a toast confirming the write. Intent is expressed with a small `Identifiable` request struct published on AppState and presented via `.sheet(item:)`, matching the app's other request types. Confidence: 0.65
